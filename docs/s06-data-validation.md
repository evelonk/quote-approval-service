# S06. Запрет подмены серверных полей черновика

**Тип цепочки:** подтверждение уже обеспеченного свойства безопасности.

## Свойство и механизм

Проверяется часть [SR-01](security-requirements.md) и [D-01](design-decisions.md):
при создании черновика HTTP-клиент не назначает владельца, роль или состояние
через JSON. Запросы выполняются от учебного менеджера `manager1` (ID 1)
для закреплённой организации 1. Здесь «клиент» означает HTTP-клиент,
а не роль представителя организации-клиента.

В [app/main.py](../app/main.py) модель `DraftInput` разрешает только
`client_org_id` и `comment`; `ConfigDict(extra="forbid")` отклоняет другие поля.
`get_user` получает пользователя и роль из БД, `get_manager` проверяет роль,
а `create_draft` назначает `owner_id=user.id`. В [app/models.py](../app/models.py)
начальный статус `Quote` задаётся сервером как `draft`.

## Сценарии и фактические результаты

В [tests/test_api.py](../tests/test_api.py) тест
`test_server_owned_fields_are_rejected_without_changing_data`
выполняет всю последовательность отдельно для каждого запрещённого поля.
Каждый случай использует новую временную SQLite-базу с учебными пользователями.

| Шаг | Запрос / проверка | Ожидаемый и полученный результат |
| --- | --- | --- |
| Штатное создание | `POST /quotes`, тело `{"client_org_id":1,"comment":"Original draft"}` | `201`, `owner_id=1`, `status="draft"`, правильные организация и комментарий; в БД одна запись |
| Подмена владельца | То же тело с `"owner_id":2` | `422`, ошибка `extra_forbidden` именно для `owner_id` |
| Подмена пользователя | То же тело с `"user_id":2` | `422`, ошибка `extra_forbidden` именно для `user_id` |
| Подмена роли | То же тело с `"role":"lead"` | `422`, ошибка `extra_forbidden` именно для `role` |
| Подмена состояния | То же тело с `"status":"approved"` | `422`, ошибка `extra_forbidden` именно для `status` |
| Проверка после каждого отказа | Сравнение полного снимка таблицы `quotes`, роли менеджера и чтение исходного черновика | Новых черновиков нет, все поля прежней записи неизменны, роль остаётся `manager`, чтение даёт `200` и прежнее содержимое |
| Штатное создание после отказа | Корректный `POST /quotes` с комментарием `After rejection` | `201`, новый ID, `owner_id=1`, `status="draft"`; в БД ровно два черновика, новый комментарий сохранён |

## Вывод и границы

В проверенных условиях `POST /quotes` отклоняет четыре запрещённых поля
без создания или изменения черновиков и без изменения роли текущего менеджера.
Штатное создание и чтение работают до и после отказа. Поле `user_id` добавлено
в набор проверок, поскольку оно прямо названо в критерии SR-01.


Проверки используют FastAPI TestClient и SQLite
