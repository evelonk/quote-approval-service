# Проектные решения безопасности Quote Approval Service

Решения ниже описывают, как сервис обеспечивает или будет обеспечивать свойства из [требований безопасности](security-requirements.md) и ограничивать угрозы из [модели угроз](threat-model.md). Статус реализации указан отдельно в каждой записи. Будущие проверки ещё не являются выполненными тестами.

## D-01. Серверная проверка личности, роли и принадлежности объекта

**Статус реализации.** Базовая часть реализована: сервер использует HTTP Basic Authentication, пароли хранятся в виде хешей Argon2, а доступные сейчас операции проверяют роль, владельца и закрепление организации. Проверки, которые зависят от ещё не реализованных версий и согласования, остаются планом.

**Контекст.** Идентификаторы предложения, версии, организации и пользователя приходят через недоверенную границу HTTP-клиента. Проверка только роли или только существования ID не защищает от чтения и изменения чужих объектов. Даже при разрешённом чтении клиент не должен получать внутренние комментарии и служебные данные согласования.

**Решение.**

- Клиент передаёт имя и пароль через HTTP Basic Authentication. Сервер находит учётную запись и проверяет пароль по Argon2-хешу. Исходный пароль в базе не хранится.
- В учебной конфигурации приложение внутри контейнера слушает `0.0.0.0`, а Docker Compose публикует его порт на компьютере только на `127.0.0.1`. Поэтому API с Basic Authentication доступен с этого компьютера, но не другим компьютерам в локальной сети.
- После успешной проверки сервер устанавливает личность и роль по найденной учётной записи. Поля `user_id`, `role` и `status` не входят в разрешённую схему тела запроса; при их передаче запрос отклоняется как недопустимый. Идентификаторы объектов из пути или параметров запроса рассматриваются только как цель операции, а права на неё определяются по серверным данным.
- Для каждой защищённой операции сервер сначала загружает целевое предложение и версию, затем проверяет роль, автора предложения, закрепление организации за менеджером, организацию клиента и допустимость запрошенного действия.
- Руководитель может принимать решения только для версий в состоянии `ожидает согласования`. Менеджер и клиент не могут выполнить это действие.
- Ответы для клиента собираются из отдельной модели данных с белым списком полей. Внутренний комментарий, служебные детали решения руководителя и правила согласования в неё не входят.
- Отказ в авторизации завершает операцию до изменения данных.

**Обоснование.** Решение о доступе принимается на сервере, где доступны доверенные данные о учётной записи и принадлежности объекта. Это не позволяет обойти ограничения заменой ID или роли в HTTP-запросе. Явное формирование клиентского ответа защищает от утечки полей даже при разрешённом доступе к самой версии.

**Сравнение вариантов аутентификации.**

- **HTTP Basic Authentication** не требует отдельного хранилища сессий, понятен при проверке через `curl` или Postman и достаточен для локального учебного MVP. Его цена — передача логина и пароля при каждом запросе, отсутствие отдельного logout и необходимость HTTPS за пределами доверенного локального окружения.
- **Серверная сессия со случайным токеном** позволяет задать срок жизни, завершить конкретную сессию и не передавать пароль при каждом запросе. При этом появляются хранилище сессий, endpoint входа и выхода, очистка просроченных сессий и дополнительные проверки.

Для текущей версии выбран HTTP Basic: сервис запускается локально, использует заранее созданные учебные учётные записи и не требует управления долгоживущими сессиями. Выбор нужно пересмотреть, если сервис станет доступен вне локального демоокружения, появятся браузерный или мобильный клиент, потребуются logout, срок жизни сессии или отзыв доступа без смены пароля.

**Контрпример и уточнение цепочки T-01 → SR-02 → D-01.** Изначально можно было предположить, что для T-01 достаточно по отдельности проверить права менеджера на предложение и версию. Контрпример: у менеджера есть два своих предложения `A` и `B`. В операцию, которая принимает `proposal_id` и `version_id`, он передаёт ID предложения `A` и ID версии из предложения `B`. Обе проверки владельца проходят, но пара ID не описывает один объект. Без проверки связи сервер может, например, отправить условия версии `B` клиенту предложения `A` или записать событие в историю не того предложения. Поэтому SR-02 и D-01 уточнены: сервер проверяет не только права на каждый ID, но и целостность связи `version.proposal_id = proposal_id`. В будущую проверку добавляется запрос с `proposal_id` предложения `A` и `version_id` из предложения `B`; ожидается `404` без раскрытия, отправки или изменения данных.

**Связанные угрозы:** T-01, T-02, T-04, T-08, T-09.  
**Связанные требования:** SR-01, SR-02, SR-03, SR-05.

**Будущая проверка:**

- **Условие:** есть учётная запись с Argon2-хешем, у одного менеджера есть предложения `A` и `B`, у другого — отдельное предложение; существуют две клиентские организации, версия в ожидании согласования и отправленная клиенту версия с внутренним комментарием.
- **Действие:** обратиться к защищённой операции без заголовка Basic, с неверным и верным паролем; проверить, что в хранилище нет исходного пароля; от имени неподходящей роли вызвать запрещённое действие; запросить чужой объект; передать в теле лишние поля `role`, `user_id` и `status`; попробовать пару ID предложения `A` и версии из предложения `B`; проверить состав ответа клиенту. Для проверки выбранного ограничения запустить сервис в учебной конфигурации и попытаться обратиться к API с другого компьютера в той же сети.
- **Ожидаемый результат:** без учётных данных и с неверным паролем сервер возвращает `401`; запрещённое для роли действие получает `403`; чужой объект и несвязанная пара `proposal_id`/`version_id` — `404`; лишние поля в теле — `422`. С верными учётными данными сервер связывает запрос с нужной учётной записью; в хранилище находится Argon2-хеш, а не исходный пароль. Отклонённые запросы не меняют объекты; ответ клиенту не содержит внутренних полей. В учебной конфигурации API недоступен с другого компьютера в сети.

**Ограничения и последствия.** HTTP Basic передаёт учётные данные при каждом запросе и не шифрует их, поэтому вне доверенного локального окружения он должен использоваться только поверх HTTPS. Компрометация пароля даёт доступ до его смены; механизма отзыва отдельной сессии нет. Решение также зависит от корректности учётных записей, ролей и привязки менеджеров к организациям. Оно не защищает от административного доступа к базе или захвата сервера, которые исключены из модели угроз. Отдельные модели ответа нужно синхронно менять при изменении API.

## D-02. Серверный расчёт и неизменяемые версии с отдельным согласованием

**Статус реализации.** Не реализовано. Серверный расчёт цен, версии и согласование описаны как выбранное направление будущей реализации.

**Контекст.** Менеджер управляет входными данными черновика, но не должен задавать цену, итоговую сумму или признак необходимости согласования. Если условия можно изменить после одобрения или перенести одобрение на новую версию, клиент получит условия, которые руководитель не рассматривал.

**Решение.**

- В черновике сервер принимает от менеджера организацию-адресата, ID позиций, количество, скидку, срок и комментарий. До сохранения сервер проверяет, что организация закреплена за менеджером, все позиции существуют, количества положительны, скидка находится в диапазоне от 0 до 100%, срок ещё не наступил, а промежуточные и итоговые значения представимы без переполнения.
- Цены сервер берёт из каталога, а базовую и итоговую суммы рассчитывает сам. Если клиент передал цену, итог или признак необходимости согласования, весь запрос отклоняется как недопустимый без создания или изменения версии.
- При фиксации сервер сохраняет в версии организацию-адресата, снимок названий и цен позиций, количество, скидку, суммы, срок и комментарий. После фиксации эти поля через API не обновляются.
- Доработка создаёт новую версию с новым ID. Решение руководителя хранится со ссылкой на конкретный `version_id` и не переносится на другую версию.
- Сервер выполняет переходы только по явно заданной таблице допустимых переходов. Перед отправкой версии со скидкой свыше 10% сервер проверяет одобрение именно её `version_id`.

**Обоснование.** Серверный расчёт убирает цену и итог из числа доверенных входов. Снимок условий и связь решения с `version_id` гарантируют, что одобрение и решение клиента относятся к тем условиям, которые они видели. Централизованная проверка переходов не позволяет обойти согласование прямым вызовом API.

**Связанные угрозы:** T-03, T-05, T-10.  
**Связанные требования:** SR-04, SR-05, SR-06.

**Будущая проверка:**

- **Условие:** в каталоге есть позиция с ценой 100; менеджер может создать предложение для выбранной организации.
- **Действие:** сначала попытаться создать черновик с неизвестным товаром, количеством 0, скидкой вне диапазона и значением, вызывающим переполнение; передать подставленные цену, итог и признак необходимости согласования. Затем создать `v1` с товаром, каталожная цена которого равна 100, количеством 2 и скидкой 15%; руководитель одобряет `v1`; менеджер отправляет её клиенту; клиент отклоняет `v1`; менеджер создаёт изменённую `v2` со скидкой 15% и пытается отправить её без нового одобрения. После фиксации `v1` попытаться изменить её адресата и цену каталога.
- **Ожидаемый результат:** все недопустимые входы и подставленные расчётные поля отклоняются без сохранения. Для `v1` базовая сумма равна 200, итоговая — 170; `v1` можно отправить только после её одобрения; `v2` не отправляется до своего одобрения; адресат, условия и суммы `v1` не меняются после фиксации и изменения каталога.

**Ограничения и последствия.** Каталог и порог согласования считаются доверенными серверными данными. Снимки позиций дублируют часть данных каталога, а новые версии увеличивают объём хранения. Изменение предметных правил потребует синхронного изменения таблицы переходов и связанных проверок.

## D-03. Атомарные переходы состояния и неизменяемая история

**Статус реализации.** Не реализовано, поскольку версии, согласование и история их состояний пока отсутствуют. Транзакции, блокировки и ограничения уникальности описаны как план.

**Контекст.** Повторные и одновременные запросы могут пройти проверку одного и того же старого состояния. Раздельная запись версии, решения и события истории при создании версии, согласовании, отправке, решении клиента или истечении срока может оставить продукт в противоречивом состоянии.

**Решение.**

- Каждая операция, меняющая версию, записывает связанное состояние и событие истории в одной транзакции PostgreSQL. Это относится к созданию новой версии, одобрению или возврату руководителем, отправке клиенту, решению клиента и системному истечению срока.
- Для операции над существующей версией транзакция блокирует её строку. После получения блокировки сервер повторно читает состояние и проверяет допустимость перехода. При решении клиента и истечении срока сервер также заново сравнивает срок с текущим серверным временем после ожидания блокировки.
- Ограничение `UNIQUE(version_id)` в таблице решений клиента даёт дополнительную гарантию: для одной версии нельзя сохранить два решения.
- Системный переход в `истекло` возможен только из состояния `отправлено клиенту`. В одной транзакции сервер меняет состояние и добавляет одно событие с исполнителем `система`, но не создаёт решение клиента. Последующие чтения уже истёкшей версии не добавляют повторных событий.
- Если запрос принятия или отклонения обнаружил наступивший срок, транзакция сохраняет переход в `истекло` и событие истории, после чего пользовательское решение отклоняется. Отказ в пользовательском действии не должен откатывать уже установленное истечение.
- История и решения добавляются новыми записями. Проектное API не содержит операций их обновления и удаления. Время и исполнитель берутся из серверного контекста.

**Обоснование.** Блокировка и повторная проверка внутри транзакции не позволяют двум запросам выполнить переход из одного старого состояния. Общая транзакция не даёт появиться версии, состоянию или решению без соответствующего события истории. Ограничение уникальности дополнительно защищает решение клиента от повторной записи.

**Связанные угрозы:** T-06, T-07.  
**Связанные требования:** SR-06, SR-07, SR-08.

**Будущая проверка:**

- **Условие:** есть черновик предложения; позднее клиенту отправлена действующая версия, для которой ещё нет решения.
- **Действие:** создать новую версию, одобрить её руководителем и отправить клиенту; одновременно отправить запросы `принять` и `отклонить`, затем повторить успешный запрос. Отдельно дождаться срока другой отправленной версии, выполнить два чтения и попытку принятия. В конкурентной проверке удерживать блокировку до наступления срока, а затем продолжить запрос решения. Для каждой операции отдельно имитировать ошибку между изменением состояния и записью события истории.
- **Ожидаемый результат:** создание версии, одобрение, отправка и решение отражаются ровно одним согласованным событием каждое. Только один из одновременных клиентских запросов успешен; сохранено ровно одно решение, повтор его не меняет. Истёкшая версия переходит из `отправлено клиенту` в `истекло` один раз; повторные чтения не создают событий, решение клиента не сохраняется, а переход и событие истечения остаются в базе несмотря на отказ в принятии. Запрос, ожидавший блокировку, проверяет новое серверное время и также не принимает истёкшую версию. При имитированной ошибке вся соответствующая транзакция откатывается, поэтому состояние, решение и история не расходятся.

**Ограничения и последствия.** Гарантия действует в пределах одной базы PostgreSQL и операций через приложение. Административные изменения БД и сбои вне транзакционных гарантий не покрываются. Проверка срока зависит от корректного времени сервера. Блокировка добавляет кратковременное ожидание для конкурентных запросов к одной версии.
