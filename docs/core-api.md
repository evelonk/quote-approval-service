# Функциональное ядро

Код подготовлен в рабочей копии от `b60bc3f`. Новые функции требуют проверки
командой перед включением в основной репозиторий. Инструкция описывает
фактически добавленные операции; результаты запусков Codex приведены в
[свидетельстве](evidence/core/README.md).

## Запуск и обновление

Используйте существующий `.env`. Для новой копии создайте его из `.env.example`
и замените обе заглушки. Не публикуйте `.env`.

```bash
docker compose up --build -d --wait
curl http://127.0.0.1:8000/health
```

`app.init_db` создает новые таблицы и выполняет добавочное обновление
`001_versions`. Старые пользователи, хеши паролей, организации и ID предложений
сохраняются. Каждый прежний черновик получает первую пустую версию и событие
создания. Отметка о выполнении находится в `schema_migrations`; повторный запуск
не создает версии заново. Преобразование данных выполняется одной транзакцией.
Это конкретное обновление текущей схемы, а не универсальный механизм миграций.
Инициализацию по-прежнему выполняет один экземпляр приложения.

Прежние столбцы `quotes.client_org_id`, `comment`, `status` оставлены для
совместимости старой базы. Они хранят исходные значения, не отражают текущее
состояние процесса и не используются для принятия решений. Текущие условия
и статус находятся в `quote_versions`. `GET /quotes/{id}` возвращает сводку
последней версии, а не устаревшие значения этих столбцов.

До обновления базы с нужными данными сохраните резервную копию:

```bash
docker compose exec -T db pg_dump -U quote_app -d quote_approval > backup-before-core.sql
```

Не используйте `docker compose down -v` для обновления. Новые тестовые пользователи
получат текущий `DEMO_PASSWORD`, пароли существующих пользователей не изменятся.
Если пароль в `.env` менялся, пароли старых и новых записей могут различаться.

## Учебные данные

| Логин | Роль и доступ |
| --- | --- |
| manager1 | Собственные предложения для организации 1 |
| manager2 | Собственные предложения для организации 2 |
| lead | Общая очередь согласования и версии со своими решениями |
| client | Отправленные версии организации 1 |
| client_peer | Второй представитель организации 1 |
| client2 | Отправленные версии организации 2 |

Каталог: товар 1 `Service A` стоит 100.00; товар 2 `Service B` — 250.00.
Каталог доступен менеджеру и руководителю; его изменение через API не предусмотрено.

## Правила расчета

- Количество положительное, до трех знаков после точки, максимум 999999999.999.
- Скидка от 0 до 100 включительно, до двух знаков после точки.
- Цена, базовая и итоговая суммы: до двух знаков после точки, максимум 999999999999.99.
- Расчет использует Decimal. Сначала суммируются цена × количество без
  построчного округления, базовая сумма округляется до 0.01 методом HALF_UP.
  Скидка применяется к этой базовой сумме, итог также округляется HALF_UP.
- Срок передается с часовым поясом и должен быть в будущем.
- Один товар встречается в версии один раз; от 1 до 100 позиций.
- При редактировании показывается расчет по текущему каталогу. При фиксации
  цены считываются заново одним запросом и сохраняются вместе с названиями.
  После фиксации изменение каталога не меняет версию.
- Денежные значения в JSON возвращаются строками, чтобы не терять точность.

## API

Все операции, кроме `/health` и документации `/docs`, требуют HTTP Basic.
В телах запросов запрещены поля, не перечисленные в схеме.

| Метод и путь | Назначение |
| --- | --- |
| GET /catalog | Каталог для сотрудников |
| POST /quotes | Создать предложение и пустую первую версию |
| GET /quotes/{quote_id} | Сводка последней версии для владельца |
| GET /versions | Все доступные пользователю версии |
| GET /quotes/{quote_id}/versions | Доступные версии предложения |
| POST /quotes/{quote_id}/versions | Новый пустой черновик следующей версии |
| GET /quotes/{quote_id}/versions/{version_id} | Прочитать конкретную версию |
| PUT /quotes/{quote_id}/versions/{version_id} | Полностью заменить условия черновика |
| POST .../{version_id}/finalize | Зафиксировать условия |
| POST .../{version_id}/approval | Одобрение или возврат руководителем |
| POST .../{version_id}/send | Отправка менеджером |
| POST .../{version_id}/decision | Решение клиента |
| GET .../{version_id}/history | История доступной версии |

`/versions` для руководителя включает ожидающие решения и версии, по которым
он уже принял решение. Для клиента возвращаются только отправленные его
организации версии, в том числе конечные. В ответах клиенту нет решения и
комментария руководителя. В клиентской истории только отправка, собственное
решение организации и истечение срока.

Ошибки: 401 — нет действительных учетных данных; 403 — запрещенная роль;
404 — отсутствующий или недоступный объект, в том числе несвязанная пара ID;
422 — неверные входные данные или срок; 409 — недопустимое состояние/повтор.

## Сквозной пример

Пароли `curl` запрашивает отдельно. Замените QID и VID значениями из ответов.
Дату срока подберите в будущем относительно дня запуска.

```bash
curl -i -u manager1 -H 'Content-Type: application/json' \
  -d '{"client_org_id":1,"comment":"Предложение"}' \
  http://127.0.0.1:8000/quotes

QID='ID-предложения'
curl -u manager1 "http://127.0.0.1:8000/quotes/$QID/versions"
VID='ID-первой-версии'
BASE="http://127.0.0.1:8000/quotes/$QID/versions/$VID"

curl -i -u manager1 -X PUT -H 'Content-Type: application/json' \
  -d '{"client_org_id":1,"comment":"Условия для клиента","items":[{"product_id":1,"quantity":"2"}],"discount":"15","expires_at":"2027-01-01T12:00:00+03:00"}' "$BASE"
curl -i -u manager1 -X POST "$BASE/finalize"
```

Ожидаются subtotal 200.00, total 170.00 и статус `pending`.
Отправка до одобрения возвращает 409; одобрение от менеджера — 403.

```bash
curl -i -u manager1 -X POST "$BASE/send"
curl -i -u lead -H 'Content-Type: application/json' \
  -d '{"action":"approve","comment":"Внутреннее обоснование"}' "$BASE/approval"
curl -i -u manager1 -X POST "$BASE/send"
curl -i -u client "$BASE"
curl -i -u client -H 'Content-Type: application/json' \
  -d '{"action":"decline"}' "$BASE/decision"
curl -i -u manager1 -X POST "http://127.0.0.1:8000/quotes/$QID/versions"
```

После одобрения статус `ready`, после отправки `sent`, после решения `declined`.
В ответе клиенту нет внутреннего обоснования. Новый черновик имеет новый ID и
номер 2, старые условия и история сохраняются, одобрение не переносится.
Для стандартного сценария задайте скидку 10: после фиксации статус сразу `ready`;
можно отправить без одобрения. Решение `accept` дает статус `accepted`.

## Сроки и конкурентные запросы

Отправленная версия после срока при чтении или попытке решения переходит в
`expired`. Отказ в запоздалом решении возвращает 409, но переход и событие
истечения сохраняются. Уже принятые/отклоненные версии не истекают.

Уточнение для срока, наступившего до отправки: версии в `ready` или `pending`
нельзя отправить/одобрить после срока. Менеджер может создать новый черновик.
Старые условия и состояние сохраняются: системный переход в `expired`
по-прежнему допустим только из `sent`. Этот пограничный случай нужно проверить
командой вместе с уточнением SR-06.

Транзакции блокируют сначала предложение, затем версию (`FOR UPDATE`).
Это также предотвращает создание двух очередных версий одновременно.
Проверка срока выполняется после ожидания блокировки с `clock_timestamp()`
PostgreSQL, а не временем начала транзакции. Решение клиента уникально по ID
версии. Состояние, решение и событие записываются одной транзакцией.

## Проверки

Обычные тесты на SQLite:

```bash
python -m pytest -q
```

Четыре конкурентных теста при этом пропускаются: SQLite не подтверждает
поведение блокировок PostgreSQL. Для отдельной тестовой PostgreSQL задайте
`CORE_TEST_DATABASE_URL` и повторите команду. Нельзя подставлять рабочую базу.
Каждый тест ядра создает отдельную случайную схему, удаляемую после теста;
для этого тестовой учетной записи нужно право CREATE SCHEMA.

CI создает собственную PostgreSQL и передает URL автоматически. Старые тесты
`test_api.py` остаются на SQLite; тесты ядра используют тестовую PostgreSQL.
Новые настройки CI подготовлены локально: успешный удаленный запуск можно
заявить только после публикации и просмотра результата.
