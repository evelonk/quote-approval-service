## Объект и воспроизведение

Исходное ядро: `e41e9b6774ba4adb66964460f56be155d664abcb`.
Проверенная версия с дополнительными тестами и усилением CI:
`5314f349a6c5abb6730cbc4880baf9bd3895db4e`.
До итогового запуска рабочее дерево было чистым. Последующий коммит добавляет
только документы и сохранённые результаты, не меняя проверенные код и тесты.

Из корня репозитория с запущенным Docker Desktop:

```bash
CORE_REPORT_DIR=/tmp/quote-m2-final sh scripts/verify_core.sh
```

В PowerShell команда оболочки должна выполняться через доступный POSIX shell
(например, Git Bash). Альтернатива — Compose напрямую с существующим доступным
каталогом отчётов и UID/GID пользователя:

```bash
mkdir -p /tmp/quote-core-results
LOCAL_UID=$(id -u) LOCAL_GID=$(id -g) CORE_REPORT_DIR=/tmp/quote-core-results \
  docker compose -p quote-core-manual -f compose.test.yaml up --build \
  --abort-on-container-exit --exit-code-from tests
LOCAL_UID=$(id -u) LOCAL_GID=$(id -g) CORE_REPORT_DIR=/tmp/quote-core-results \
  docker compose -p quote-core-manual -f compose.test.yaml down --remove-orphans
```

Скрипт записывает SHA и состояние Git; собирает Dockerfile и запускает тесты
в отдельной PostgreSQL 16 с tmpfs. Порт БД не публикуется, `.env` не нужен,
пользовательские тома не подключаются. После завершения скрипт убирает только
свою сеть и контейнеры. При сбое сборки или тестов возвращается ненулевой код.

Окружение: Python 3.12 в `python:3.12-slim`, версии библиотек закреплены в
`constraints.txt`; фактическая среда и сборка видны в протоколе. Сборка локальная
на Linux arm64 в Docker Desktop, удалённый CI выполняется на Ubuntu runner.

Тесты находятся в [tests](../../../tests/); новые граничные проверки —
[test_core_review.py](../../../tests/test_core_review.py).
Сценарии сравнивались с критериями SR, а не только с ответами текущего кода.
Например, для неизменности адресата создана вторая разрешённая менеджеру
организация: тест не может случайно пройти за счёт одного запрета чужой организации.
Для равенства сроку время фиксируется на уровне серверных часов; поведение
настоящей PostgreSQL после ожидания блокировки отдельно подтверждает существующий
конкурентный тест без подмены часов.

## CI на опубликованной версии

Через публичный API проверен [run 42627635277](https://github.com/evelonk/quote-approval-service/actions/runs/42627635277)
на исходном `e41e9b6774ba4adb66964460f56be155d664abcb`.
Статус completed/success; шаги Run tests, Build Docker image, Record checked
commit и Save test results успешны. Артефакт test-results существует, не истёк,
SHA256 опубликован в [метаданных](m2-20261110/github-actions.json).
Содержимое удалённого ZIP-артефакта здесь не скачивалось: точное число тестов
того запуска по метаданным не утверждается.

В workflow найден пробел контроля: pytest возвращает успех и при пропуске всех
PostgreSQL-тестов. Добавлен шаг `Verify PostgreSQL test coverage`, который
проверяет XML: нет failures/errors/skips, все четыре конкурентных сценария
присутствуют. Пустой отчёт также считается ошибкой. Дополнительно задан лимит
job 15 минут против зависшего конкурентного теста или недоступной БД.
Новый локальный стенд выполняет тот же контроль после pytest.

Проверка самого контроля: копии настоящего XML с искусственным skipped,
удалённым конкурентным тестом и пустым набором отвергнуты —
[результат](m2-20261110/report-guard-check.txt).
Положительный случай подтверждён итоговым прогоном 72 тестов.

Изменённый workflow на `5314f34` **ещё не выполнялся в GitHub Actions**:
push запрещён пользователем. Локальная сборка и тесты не подменяют удалённый
запуск Actions. После разрешённой публикации команда должна проверить новый
run на точном SHA, скачать test-results и сверить checked-commit.txt.

## Замечания и ограничения

1. Пробелы тестов закрыты 16 новыми случаями. Дефект приложения в проверенных
   сценариях не подтверждён; бизнес-логику и SR ради зелёного прогона не меняли.
2. HALF_UP, порядок суммирования/округления и восстановление процесса после
   срока до отправки уже определены в core-api.md и SR-06. Тесты подтверждают
   их реализацию. Содержательное принятие этих правил командой остаётся
   отдельной человеческой проверкой, а не выводом pytest.
3. Личное воспроизведение M2 и повтор нового CI после push остаются открытыми
   действиями. Команда может повторить локальную проверку одной командой выше.
4. Здесь нет нового HTTP smoke-прогона отдельно запущенного uvicorn, проверки
   после перезапуска рабочего тома, SAST/SCA/поиска секретов, нагрузки или
   проверки с другого физического компьютера. Они не объявлены выполненными.
5. Предыдущий [протокол](README.md) относится к другой рабочей копии и сохранён
   как историческое свидетельство; этот прогон привязан к новому коммиту.

По содержанию это независимая проверка рубежа ядра S07 и воспроизводимости S08.
Материалы курса: `seminars/S07/README.md`, `seminars/S08/README.md`, `evidence.md`.
S08 требует успешный Actions именно своего продукта и повтор другим участником;
автоматическую работу Codex нельзя выдавать за самостоятельное выполнение M2.
